## Working Contract

- **Teaching-first (primary goal):** the owner is using this project to learn full-stack engineering to a level that prepares them for a Google software-engineering interview and role. Every feature/phase/task therefore runs as **plan → teach → implement → teach**: (1) *before* writing code, present a plan and explain the design — what we're building, the options considered, the trade-offs, and *why* this approach — in plain terms, and get agreement; (2) *after* implementing, walk through the implementation — the files, the functions, and the concepts they demonstrate. Prioritize transferable, interview-relevant fundamentals (data structures & algorithms, system design, concurrency/consistency, API & schema design, security/trust boundaries, testing strategy, complexity trade-offs) over framework trivia; when a task naturally exercises one of these, name it and go a level deeper. This checkpoint is mandatory and supersedes pure autonomy — do **not** silently bundle tasks past a plan/teach step (see the self-paced note below).
  - **Explain from scratch, concisely:** assume the owner has almost no prior software knowledge — define the basics (e.g. what Express is, what a `package.json` is) rather than assuming them, and never leave a term or sentence resting on unstated jargon. But the owner learns *fast*, so keep every explanation tight and high-density: short, plain-language, no padding or repetition. Aim for the minimum words that make a concept click.
- **Atomic iteration, paced by the teaching checkpoint:** work through `backlog.md` tasks one at a time in order. Unlike a fully autonomous run, each task pauses at the plan/teach checkpoint above before implementation and delivers its implementation walkthrough before the next task starts — so tasks are **not** silently bundled. Each task still closes fully before the next: TDD → implementation → full suite green (`npm test`, `npm run lint`, typecheck; `supabase test db` if the DB changed) → docs/backlog updated. Stop and ask when a task turns on a product/design decision that isn't derivable from `docs/` or existing tests. Anything touching a listed "known gap" always stops and asks; never invent a decision there.
- **TDD:** every code task starts with the `.test.ts`/`.spec.tsx` file (or pgTAP equivalent), agreed as correct, *before* any implementation code is written. "Agreed as correct" means: reviewed against `docs/` and the phase DoD, with the reasoning made explicit, before implementation proceeds.
- **Documentation-first close-out:** a task isn't done until `backlog.md` has it checked `[x]` and any `.md` file whose claims changed (e.g., `ARCHITECTURE.md` for a new service, `DATABASE.md` for a schema change) is updated in the same turn.
- **Skills system:** read the relevant skill(s) in `.claude/skills/` before starting a coding task; if a needed convention doesn't exist yet, add a new `.claude/skills/<name>/SKILL.md` (with `name`/`description` frontmatter) alongside the code, not after.
- **Commits:** only when explicitly asked — self-pacing through tasks doesn't imply auto-committing. Exception: an explicitly requested unattended/background autonomous run over `backlog.md` commits **and pushes to `origin`** after each task closes (full suite green + docs updated), giving a checkpoint to recover from if something later in the run goes wrong.
- **Branching (owner decision, revised 2026-08-04 — supersedes the 2026-07-28 `dev` convention):** every feature and every phase gets its own branch **off `main`** (e.g. `phase5-gamification-stats`), merged **straight back into `main`** once it closes (full suite green + docs updated). **There is no `dev` branch** — it was removed because it added a second merge step and a second place for work to sit unmerged, which in a solo workflow bought nothing and made planning/handoff artifacts invisible to any session that checked out the default branch. Solo-dev workflow, no PR review step needed, but still a real branch + merge rather than committing straight to `main`. Consequence to keep in mind: `main` is now the working trunk rather than "the last fully-completed phase", so anything a future session needs to find — plans, handoff notes, docs — has to reach `main` to be discoverable.

## Money-Equivalent Logic Rule

Points, bonuses, QR tokens, and anything else that affects a user's earned rewards are computed and minted **only** in the Node.js API, never trusted from a client claim, and never computed client-side even for display — always fetched from the server's authoritative value. See `docs/ARCHITECTURE.md` §3 and §8 for why.
